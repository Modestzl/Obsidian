# Как довести правила discount.php до всех мест показа

Дата: 09.10.2026. Текущее состояние после пользовательского обновления product.php. Анализ без выполнения PHP, БД, HTTP-точек проекта и изменения исходников.

## Основной вывод

Настройки скрытия уже заданы. Обработчик есть в getProducts/getTotalProducts, но другие пути его обходят. Требуется завершить распространение одного правила, а не заново настроить 239=>500. Ранее предложенный общий план следует читать с учётом этого документа.

## Точная семантика текущего обработчика

Источник: amital_ru/discount.php::$categrory_product_remain. При положительном значении скрывать товар с p.quantity<=0 и p.price<порога, если он привязан к корню или потомку. При значении 0 скрывать все товары с p.quantity<=0. Текущий код так же трактует отрицательный порог, поэтому настройками следует пользоваться только с неотрицательными значениями. Несколько подходящих правил объединяются OR: одного достаточно для скрытия. Отсутствие ID дочерней категории в массиве не отменяет правило предка. Удаление частного правила потомка не отменит родительское. 500 ровно не скрывается правилом 239=>500, но может скрываться другим подходящим правилом. Используется базовая цена, не цена с персональной/категорийной скидкой.

Правила относятся ко всем перечисленным категориям, не только к канцтоварам. category_nodiscount и category_discount управляют скидками, не заменяют categrory_product_remain. Скрытие не должно менять status или удалять товар.

## Конкретная доработка

1. В модели каталога сделать единый генератор SQL-условия исключения из categrory_product_remain. Оба существующих блока заменить его вызовом без изменения смысла. Корни и правила читать один раз за запрос. Не использовать глобальное include_once внутри разных методов без сохранения конфигурации: переменные include имеют локальную область видимости и последующий метод может их не получить. Не включать весь discount.php в глобальную область повторно так, чтобы переопределить переменные скидок. Предпочтителен отдельный загрузчик правил с кешированием в объекте на время запроса; стабильный путь от DIR_APPLICATION к корневому discount.php после проверки окружения.
2. В getProduct добавить то же SQL-условие к выборке с алиасом p (или эквивалентную проверку сразу после получения строки). При отсутствии/скрытии сразу возвращать false ДО min_sale и чтения query->row: сейчас чтение полей начинается до проверки num_rows. Это закроет все формы прямой ссылки через модель. Штатная ветка карточки уже формирует not_found; заголовок строки product.php:874 в контроллере собирается как SERVER_PROTOCOL + '/1.1 404 Not Found', что требует проверки/исправления формата HTTP при патче: если SERVER_PROTOCOL='HTTP/1.1', строка будет некорректной. Не считать наличие текста 404 доказательством правильного HTTP-ответа.
3. Проверить все потребители getProduct. Не добавлять false в списки, пропускать скрытый товар до чтения его полей. Поправить отдельные SQL списков ДО LIMIT и их подсчёты, а не только пропускать после выдачи. Покрыть кешированные массивы, которые возвращаются без повторного getProduct. Для связанных товаров считать total с тем же условием. Не менять исторические строки заказов.
4. Sphinx — отдельный необходимый этап. Для небольшого количества исключаемых товаров возможен мост: получить из MySQL точный набор product_id, скрытых по текущим правилам, и исключать его в товарных запросах Sphinx до LIMIT, также в COUNT и группах. Для API клиента использовать исключающий фильтр по соответствующему атрибуту ID, для SphinxQL — NOT IN по проверенному product_id_attr. Пустой список не формирует NOT IN (). Это направление реализации, не готовая строка для всех индексов: схема ID у products_name/products/main требует подтверждения. Большие списки ID нельзя отправлять без оценки размера и задержки; перед выбором измерить число скрытых товаров и план MySQL. Не загружать весь каталог в PHP.
5. При большом наборе исключений выбирать атрибут видимости в действующих индексах или поддерживаемое выражение по существующим атрибутам. Источником остаётся discount.php; при индексируемом признаке изменения файла, цены, остатка и категорий должны обновлять признак. Иначе изменение настройки в файле не вступит в силу в поиске. Наличие categories_filter не доказывает включение предков: локальные шаблоны sphinx.conf.in:43–48 и sphinxsearch.php:220–221 заполняют прямые категории. Передавать только 239 без потомков нельзя без проверки индекса. Версия и схема рабочего Sphinx неизвестны; окончательный способ выбирается после проверки, не требуется заранее переделывать поиск целиком.
6. Вспомогательные API, используемые constructor/gifts/featured, должны получать те же исключения или корректно применять их до собственной пагинации. Финальная проверка MySQL перед показом защищает от устаревших данных, но не исправляет счётчики и наполнение страниц сама по себе.
7. Кеши учитывать вместе с изменением правил: ключ/инвалидация по конфигурации discount.php решает смену правил, но не смену цены/остатка. Нужна также инвалидация при обновлении данных либо проверка текущей видимости при чтении с наполнением списка. В buyingwith TTL=43200 (product.php:910). Не очищать кеш vQmod на рабочем сервере вслепую.

## Что получит владелец после доработки

Управление остаётся в discount.php: category_id=>порог; 0 означает скрытие любых неположительных остатков в этом дереве; удаление правила убирает только его, но не правила предков. Показывать/скрывать вручную отдельные товары не нужно. Для примера 594688 при подтверждённой принадлежности дереву 239, базовой цене<500 и quantity<=0 товар отсутствует в категориях, поиске, товарных подсказках, модулях и карте сайта, а прямая ссылка возвращает корректный 404. После поступления товар снова допускается к показу с учётом прочих ограничений и согласованного обновления индекса/кешей.
