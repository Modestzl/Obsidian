# Скрытие дешёвых канцтоваров без складского остатка

Дата: 07.10.2026. Статический анализ локальной копии. Исходники, БД и сервер не изменялись.

## Требуемое правило

Скрывать товар, если одновременно: он привязан к «Канцтоварам» или любому потомку; цена меньше 500 рублей; складской остаток равен нулю. Остатки розничных магазинов не отменяют правило. Цена ровно 500 не подпадает. Отрицательный остаток не включён в буквальный запрос; практическое расширение до quantity <= 0 нужно определить перед патчем. Базовая цена и окончательная цена со скидкой могут различаться: требуется выбрать основание порога.

Это объясняет возможность прямого открытия карточки при отсутствии товара в категории; поведение сервера не проверено.

Он не скрывает карточку и не ограничен канцтоварами. admin/view/template/common/home.tpl:209–211 содержит настройку минимальной цены товара, доступного только в магазинах. - getFinalPrice():322–327 рассчитывает цену со скидкой и округлением, поэтому p.price не всегда совпадает с ценой покупателя.
- vqmod/xml/sphinx_search.xml:179 и далее может менять getProduct(), включая условие статуса. Применимость и настройки сервера неизвестны. Сохранённый vqcache для модели каталога товаров не найден.

## Рекомендуемая реализация

Общее правило видимости товара на уровне каталога, с проверкой принадлежности через product_to_category JOIN category_path и path_id корневой категории. Не опираться на путь в URL: товар может иметь несколько категорий или открываться без пути.

1. Применить одинаковое условие к спискам и их подсчётам до LIMIT; решить, заменяет ли новое правило прежний более строгий запрет всех нулевых канцтоваров.
2. Закрыть прямую карточку скрытого товара штатным ответом 404.
3. Согласовать Sphinx, автодополнение, рекомендации, акции, карту сайта и выгрузки. Проверить потребителей getProduct() перед изменением его результата; простое возвращение false может ломать места без проверки.
4. Проверить добавление товара по идентификатору в корзину, если требуется исключить также покупку.
5. При обновлении цены/остатка пересчитывать видимость автоматически. Не отключать массово status вручную: обмен может перезаписать его, а самостоятельное восстановление статуса может затронуть товары, отключённые по другим причинам.

## Подробный порядок реализации — 09.10.2026

Это план, не применённый патч. Пример ниже предполагает базовую цену p.price, ровно нулевой остаток и подтверждённый корень 239. Для конечной цены со скидками потребуется согласовать вычисления MySQL, PHP и Sphinx; персональные скидки могут сделать видимость зависимой от покупателя.

### 1. Уточнить правило и сверить сервер

Зафиксировать цену (базовая/конечная), quantity = 0 или <= 0, отмену нынешнего запрета всех нулевых канцтоваров и поведение корзины. Сохранить ручное выключение товара, даты доступности, ограничения магазина и остальные действующие условия. Сверить только нужные файлы сервера, версию PHP, применимые XML vQmod, активные настройки Sphinx, фактическую конфигурацию индекса и путь обновления остатков. Для БД достаточно согласованной выборки категории 239, её дерева и связей/числовых полей товара 594688; полный дамп и доступы в документах не нужны.

### 2. Единое условие MySQL

Логическое дополнение к действующему WHERE в выборках с алиасом p:

```sql
AND NOT (
    p.price < 500
    AND p.quantity = 0
    AND EXISTS (
        SELECT 1
        FROM oc_product_to_category visibility_p2c
        INNER JOIN oc_category_path visibility_cp
            ON visibility_cp.category_id = visibility_p2c.category_id
        WHERE visibility_p2c.product_id = p.product_id
          AND visibility_cp.path_id = 239
    )
)
```

Это иллюстрация для разработчика, не самостоятельная команда к БД. В PHP использовать DB_PREFIX, проверенный ID категории и общий генератор условия для фиксированных доверенных SQL-алиасов. EXISTS не умножает строки товара при нескольких привязках. Проверить индексы и план запроса на тестовой БД, не добавлять индексы вслепую.

Применять до сортировки, LIMIT и подсчёта. В getProducts/getTotalProducts убрать или заменить старые блоки hide_zero_stock; иначе товары от 500 без остатка останутся скрыты. Проверить getProductSpecials/getTotalProductSpecials, getLatestProducts/getPopularProducts/getBestSellerProducts, промо и связанные товары. При централизованной фильтрации getProduct обработать false у всех потребителей; уже найден getProductEcommerceInfo():1306–1322, читающий поля без проверки. Результаты с false нельзя помещать в массив карточек.

### 4. Поиск Sphinx

searchByQL():525, search():207 и searchTooltips():436 требуют согласованного правила. Считать результаты, общий итог и группы с одним фильтром. Не отбрасывать товары только после LIMIT: страницы и числа станут расходиться.

Предпочтительное направление при подтверждении среды — отдельный числовой атрибут hidden_stationery в действующих товарных индексах. 1 означает выполнение всех трёх условий; запросы фильтруют hidden_stationery=0. Добавление требует адаптации фактического источника индекса и всех путей обновления цены, остатка, категории и дерева. При перемещении категории пересчитывать затронутое поддерево. Шаблоны нельзя считать готовыми серверными конфигами. Индексировать и переключать индекс только после теста и отдельного разрешения на серверные действия.

Если категории уже содержат предков и версия Sphinx поддерживает нужное выражение, оценить вариант фильтра по существующим атрибутам. До проверки схемы/версии готовый SphinxQL не давать. Не менять status массовым SQL. Видимость должна зависеть от актуальных данных; обмен сохраняет цену и остатки обычным образом и обновляет индекс/кеш. Конкретный действующий путь обмена этой задачей пока не установлен.
