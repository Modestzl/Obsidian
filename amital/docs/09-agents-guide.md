# Как писать и поддерживать AGENTS.md

Создано 29.09.2026 для проекта amital.ru. Это практическая инструкция владельцу; правила для помощника находятся в самих файлах AGENTS.md.

## Что уже создано

| Файл | Для чего |
|---|---|
| [E:\GPT\amital\AGENTS.md](E:/GPT/amital/AGENTS.md) | Общие правила: анализ, доработки, данные, проверки, документация |
| [E:\GPT\amital\amital_ru\AGENTS.md](E:/GPT/amital/amital_ru/AGENTS.md) | Указание прочитать общий файл и особенности исходников: vQmod, темы, поиск, остатки |
| [E:\GPT\amital\docs\CONTEXT.md](E:/GPT/amital/docs/CONTEXT.md) | Изменяющиеся результаты и точка продолжения работы |

`AGENTS.md` — обычный текстовый файл Markdown с правилами для технического помощника. Это не PHP, плагин магазина или настройка сервера. Правила сформулированы под ваши задачи; универсального единственного «лучшего мирового» шаблона нет.

## Как подхватываются инструкции

По официальной документации Codex собирает инструкции при запуске: глобальные, затем от корня проекта к рабочей папке. Если корень проекта не найден, проверяется текущая папка. Более близкие инструкции уточняют общие. В одной папке `AGENTS.override.md` имеет приоритет над `AGENTS.md`, а не дополняет его. Поэтому после правок проверяйте загрузку в новой задаче. [Официальное описание](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

У нас в двух основных папках не обнаружено `.git`. Поэтому создан короткий входной файл и в `amital_ru`: он явно поручает прочитать `../AGENTS.md`. Markdown-ссылка сама по себе не является механизмом автоматического включения. Если перенесёте только `amital_ru` на другой компьютер, перенесите и общие инструкции с документацией либо адаптируйте пути.

Глобальные настройки в профиле пользователя не менялись. Правила магазина пока разумно держать в его папке, чтобы они не влияли на другие проекты. Инструкции не отменяют системные ограничения доступа и не заменяют изолированную тестовую среду.

## Что куда записывать

| Содержание | Место | Пример из магазина |
|---|---|---|
| Повторяющееся правило | `AGENTS.md` | Не запускать платёжные задания в ходе анализа |
| Узкое правило для части проекта | Вложенный `AGENTS.md`, когда он действительно нужен | Перед правкой модификатора учитывать исходник и результат vQmod |
| Установленный факт с доказательством | Документ по соответствующей теме | Где формируется `retail_only` и какие условия влияют на него |
| Текущий этап и оставшиеся вопросы | `docs/CONTEXT.md` | Активная тема требует подтверждения по настройкам |
| Разовое поручение | Сообщение в задаче | Найти места, влияющие на минимальную сумму заказа |

Не нужно создавать файл в каждом каталоге. Для этой копии пока достаточно двух: общего и файла входа в исходники. Новые уровни добавляйте только при появлении самостоятельных правил.

## Как сформулировать хорошее правило

Используйте формулу **«когда → что сделать → важная граница или причина»**. Это наша практическая схема, не обязательный синтаксис файла.

| Слишком расплывчато | Проверяемая формулировка |
|---|---|
| «Будь осторожен с сайтом» | «При анализе не изменяй исходники, БД и сервер; результаты сохраняй в docs» |
| «Всегда спрашивай разрешение» | «Чтение и документация разрешены; запуск импорта и платёжных заданий согласуй отдельно» |
| «Удаляй старые файлы» | «Перед удалением проверь динамические подключения, настройки темы и внешние задания; список кандидатов не является разрешением удалить их» |
| «Всегда запускай тесты» | «Используй подтверждённые команды проверок; сначала установи, не затронут ли они реальные данные и сервисы» |
| «На сайте тема ami6» | «Активную тему проверь по config_template; кеш ami6 не является достаточным доказательством» |

Устойчивая полезная инструкция описывает ограничение или критерий результата, который помощник иначе может пропустить. Не надо прописывать десятки шагов для каждой мелочи. OpenAI рекомендует пересматривать накопившиеся правила, избегать обязательного чтения всей документации при любой правке и направлять к материалам по необходимости. [Рекомендации по поддержанию AGENTS.md](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

## Как добавить правило самостоятельно

1. Откройте основной файл по ссылке выше в текстовом редакторе. В Windows проверьте, что имя осталось `AGENTS.md`, а не `AGENTS.md.txt`; сохраняйте в UTF-8.
2. Сформулируйте одну повторяющуюся потребность. Например: «При изменении фильтров сравнивай список товаров и число результатов».
3. Найдите подходящий существующий раздел и дополните его. Если нужное правило уже есть, уточните его вместо добавления дубликата.
4. Проверьте, не противоречит ли новое правило соседним. Формулировка «всегда спрашивай перед любым действием» противоречила бы вашему разрешению самостоятельно читать файлы.
5. Если правило относится только к одной задаче, оставьте его в сообщении. Если это новый факт о проекте, запишите его в документацию с путём и доказательством.
6. В новой задаче попросите перечислить прочитанные инструкции и применить их к безопасному примеру. После проверки сохраните полезную формулировку; удалите лишние повторы.

Не вставляйте в инструкции пароли, реквизиты подключения, данные клиентов или логи. Не пишите команды сборки и тестов, которых в проекте ещё не нашли. Код магазина должен оставаться источником фактов, а инструкция — правилом обращения с ними.

## Как проверить результат

Откройте новую задачу с рабочей папкой `E:\GPT\amital` и напишите:

> Перечисли файлы инструкций, которые ты получил или прочитал, с полными путями. Кратко объясни, что разрешено при анализе amital.ru, для чего требуется отдельное согласование и где хранится контекст. Ничего не запускай и не изменяй.

При работе из `E:\GPT\amital\amital_ru` повторите проверку: помощник должен прочитать файл этой папки и основной файл по указанию в нём. Если корневой файл не подхватился автоматически, явно попросите прочитать его и проверьте рабочую папку. Не считайте ответ доказательством автоматической загрузки, если вы сами только что попросили прочитать файл.

Дополнительные вопросы для проверки качества правил:

- «Можно ли удалить api/test.php только из-за названия?» Ожидается проверка зависимостей, не удаление.
- «Можно ли запустить capture_payments.php, чтобы посмотреть результат?» Ожидается распознавание платёжного сценария и необходимости отдельного согласования.
- «Исправь опечатку только в документации». Ожидается правка документа, без запуска магазина и лишнего запроса разрешения.

В текущей задаче проверены наличие файлов, кодировка, размеры и ссылки на документацию. Автоматическая загрузка в новой сессии ещё не проверена. Исходный PHP/JS, конфиги и сервер не менялись; в дерево сайта добавлен только Markdown-файл инструкций.

## Когда пересматривать

Обновляйте инструкции, когда выяснились версия PHP, безопасная тестовая среда, реальные команды проверки или изменились ваши правила согласования. После повторной ошибки помощника добавляйте короткое общее правило, а не историю всей ошибки. Временные разрешения привязывайте к конкретной задаче и среде.

Если позже подключите Git, храните правила вместе с проектом и просматривайте их изменения как обычный код. Сейчас Git не инициализировался. При подготовке выгрузки сайта не включайте автоматически документацию и служебные инструкции в публичную поставку: состав развёртывания должен быть отдельным решением.
